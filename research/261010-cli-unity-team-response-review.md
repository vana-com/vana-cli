# CLI and Unity: recheck after the team discussion

Date: 2026-10-10, Australia/Brisbane. Owner: this follow-up and the [original comparison](./261009-cli-unity-surfaces-discrepancy-research.md) in `vana-cli/research`. This is research and a recommendation, not an accepted migration plan.

## My take

Volod supports the central argument: we should stop independently maintaining the same plumbing. His public-source and release concerns are real. They change the recommendation from “move the CLI first” to “give shared plumbing one owner first, while preserving public source and independent CLI delivery.”

The CLI belongs in the map of Unity surfaces. Its source does not have to live in the Unity repository for that to be true. It can be the executable schematic for the same system by calling the same authorities and implementations. Moving files would not, by itself, remove duplicated rules. Separate repositories do not require separate rules either.

The discussion mixes four choices: where source lives, whether people can inspect it, who owns common behavior, and how each product releases. Decide them separately. The intended rule remains: one authoritative owner for each responsibility, one shared implementation where practical, and runtime adapters that conform to the same behavior where Node, Rust, Dart and browsers cannot execute the same code.

## What the MCP implementation actually does

The CLI configures the external Personal Server producer with the Web scope-request URL. The new Web page preserves `ps_origin` through sign-in, takes the owner from the active wallet, and verifies the server owner and active server registration through trusted Gateway origins before reading the request. It supports fragment-token reads and explicit signed loading; the older CLI link without a fragment token still has a supported path.

Approval signs the exact body and selected offered additions; denial has its own endpoint. The signer is Account, and Web verifies that the returned signature recovers the expected owner. Account's silent-signing policy independently checks first-party origin, claim shape, method/path, body hash, freshness, active owner and registered server; refusal falls back to visible confirmation. These are silent-signing eligibility checks, not mandatory checks for every manually confirmed signature. Approval retains Account confirmation by default; silent approval is an explicit environment option. The server response supplies the resulting grant state.

## “Grant union in three places” needs a precise count

I found two independent app-grant union implementations in the inspected CLI, Unity and installed SDK sources: SDK and Web. CLI's `src/core/grant-union.ts` reexports the SDK planner. It adds CLI-worded conflict handling and CLI request preparation, not a third merge algorithm.

| Location                         | What it owns                                                                                                                    |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| SDK 4.3.1                        | Scope preservation/removal and live-grant lookup primitives.                                                                    |
| CLI                              | Calls SDK; owns preliminary owner inference, lookup and fallback before making a request.                                       |
| Web                              | Independently reads the actual approving owner's grant; plans scopes, expiry and version, then repeats the read before signing. |
| Desktop / Mobile paths inspected | Advance or rebase versions and register supplied scopes. They do not perform the same preservation union.                       |
| MCP                              | Extends a server-controlled connection's access; returned-scope unions are a different operation.                               |

There may be another implementation in an external repository. The screenshot does not identify it, and this review does not claim a global count across uninspected services. Calling every union-shaped view or every registration call another copy would be misleading.

The two planners are also not interchangeable without agreement on behavior. Installed SDK 4.3.1 drops unparseable carried scope entries and filters inactive rows before choosing the highest live version. Web preserves string entries and chooses the highest row before treating revoked/expired as inactive. They could disagree if a history includes an older live row and a newer revoked row. Gateway intends one row per owner/app, so this is a conditional difference, not an observed live failure. Web also owns expiry/version output beyond the SDK scope-only union result.

Unity Web is pinned to SDK 4.1.0, whose installed JS/type distribution contains neither `mergeWithLiveGrant` nor `unionGrantScopes`; CLI is pinned to 4.3.1. Web adopting this helper therefore needs a compatible browser-facing export/version and must retain its authoritative pre-sign owner read, expiry/version handling and failure behavior. Removing Web's file alone would not prove that.

## Finding 4 still has a separate delivery join

Direct requests remain read-ready until consumer acknowledgment or supported Personal Server fulfillment reporting completes them. Web's request store distinguishes approved/read-ready from completed, and the continuation waits for actual completed delivery. SDK 4.3.1's approved-read controller calls consumer-ack after successful reads, though it swallows ack failure; even that return value is not durable completion proof.

CLI `app read` calls lower-level Personal Server reading, or enclave jobs reading, rather than those approved-read controller methods. Its inspected source contains no consumer-ack call. The lower-level SDK reader has no request ID or acknowledgment operation.

Working Web PS Lite can report served scopes itself, which can complete a CLI read's underlying request. The store matches owner/grant/scope and credits the newest matching request. Thus “CLI never completes a DCR” would overstate the evidence. The remaining issue is conditional: on a lane without a working server-side receipt producer, the inspected CLI consumer supplies no explicit completion acknowledgment. Current Full/enclave receipt behavior was not established by inspecting these two repositories.

The needed proof is a multi-scope Direct request, real approval, CLI reads over each supported delivery lane, and observation of the specific DCR and continuation reaching their terminal state. Choosing a grant ID alone is not an unambiguous request identity when several requests can share a grant.

## Public source and binary delivery are separate choices

Kahtaf is technically right that software can be distributed as a binary without public source. Claude Code demonstrates that commercial distribution choice: [official setup](https://code.claude.com/docs/en/setup) and [official license](https://github.com/anthropics/claude-code/blob/main/LICENSE.md). That analogy does not settle Vana's privacy or source-availability decision.

CLI is currently a public MIT repository; Unity is private. These were checked through GitHub repository metadata. Unity has narrower package licenses: Desktop Apache-2.0 and public MIT `service-auth`; absence of a repository-wide detected license does not mean every package is unlicensed. Public-source scrutiny is a concrete reason to preserve access to maintained CLI code. It helps users inspect handling of their data and keys; it does not itself prove runtime privacy, backend behavior or equivalence of release artifacts.

CLI is already more than a terminal executable. It publishes npm and seven JS import entry points: root, server, React, core, runtime, connectors and CLI. Its README explicitly recommends runtime/connector imports for app integration. Publishing only standalone binaries must not silently discard those external APIs. Their actual consumers were not inventoried in this review.

Existing SEA distribution is an executable launcher plus an adjacent emitted-JavaScript/dependency payload. It avoids requiring the user's Node installation; it is not a claim that all implementation is compiled into one opaque artifact. Signing/notarization support establishes an available distribution mechanism, not a source audit or proof that an individually inspected release is signed.

A private monorepo can publish public npm packages: Unity already does. Preserving a publicly inspectable maintained source tree and history is another obligation. If CLI moves into private Unity, the proposal needs an explicit public source path, package licensing and publishing owner rather than assuming a binary or npm tarball preserves the current open-source experience.

## CI concerns are real, but one repository does not require one pipeline

Unity already releases Desktop and service-auth independently, with separate tags and workflows. CLI already separates some worker/frpc delivery and publishes npm after the binary release. Physical co-location does not require every CLI change to rebuild or release every app.

The concern is still concrete in today's configuration. Unity PR CI has no workflow-level path filter and installs/checks Account, Web and Desktop broadly. A naive CLI move would inherit those gates. Mobile already has a dependency-closure change gate, showing that narrower checks are feasible. No CI timings were collected here; “would be slower” is an expectation about those additional jobs, not a measured result.

## What I would agree with, and what I would ask the proposal to cover

Start with grant union. It is small, already has focused behavior tests, and exposes why “shared” needs an exact contract: owner binding, scope preservation, explicit removal, expiry, version, revoked rows and failed live lookups. Use the existing SDK/protocol owner where that is the correct responsibility. Verify all actual callers before deleting their implementations. Desktop and Mobile also need an explicit decision about whether their supplied-scope registration paths should preserve previous access; importing a helper only into CLI and Web would not decide that.

Then address collection policy and journey joins. Protocol utilities alone do not govern skipped records, empty data, checkpoint commitment, local durability versus ingest/sync, cancellation, provider-account partitioning, capability admission, register→claim, or read→completed-request. Volod's intention is compatible with covering these; the offered first task does not yet specify their owners or proof.

| Responsibility                               | Owner to use or settle                                                   | Surface-specific effects remain                            |
| -------------------------------------------- | ------------------------------------------------------------------------ | ---------------------------------------------------------- |
| Identity and constrained owner signing       | Account authority and its supported client transport                     | Browser redirect, embedded wallet, terminal/native handoff |
| Grant/payment/signature protocol rules       | Existing SDK/protocol/service owner                                      | Product review UI, CLI remedies, wallet/app-key access     |
| Connector artifact and collection guarantees | Connector/protocol contract owner, with common host cases                | Node Playwright, Rust/native browser, Dart WebView         |
| Data storage, ingest and sync semantics      | Personal Server / registry/storage owners; check existing client mirrors | Host lifetime, local persistence and device bridge         |
| Request readiness and consumption            | Web DCR/service authority with explicit consumer completion              | App continuation, reads, UI status                         |
| Release packaging                            | Each product's release owner                                             | npm, signed executable, desktop/phone packaging            |

This is a proposed ownership direction, not a new universal library. Unity already has shared app-runtime and owner-data packages, while protocol and Personal Server core have external owners. Check those owners before inventing another layer. The owner-data client explicitly mirrors server sync workers, and CLI escrow helpers explicitly mirror Account; those are concrete consolidation candidates alongside grant planning and host collection policy. [Unity ownership boundary](https://github.com/vana-com/unity-surfaces/blob/6cefcc41a593dc5f7839a6d31aa115669429cfe7/docs/adr/0001-app-surface-boundary.md#L3), [sync-worker mirror](https://github.com/vana-com/unity-surfaces/blob/6cefcc41a593dc5f7839a6d31aa115669429cfe7/packages/owner-data-client/src/owner-data-client.ts#L63), [Account escrow mirror](https://github.com/vana-com/vana-cli/blob/f99bec8b235c2c5fdb2bd11875051fb0632f7bfb/src/core/escrow-authorization.ts#L13), [existing SDK tracker baseline](https://github.com/vana-com/unity-surfaces/blob/6cefcc41a593dc5f7839a6d31aa115669429cfe7/docs/vana-sdk-consolidation-candidates.md#L24).

My recommendation is to preserve public CLI source and independent delivery now, consolidate demonstrated shared rules, and keep CLI in the system map as an executable view of the same plumbing. Revisit repository placement when the benefit of atomic cross-surface changes justifies the visibility, packaging, compatibility and CI work. The condition of success is that the surfaces use the same authoritative behavior, not that their folders share a parent.
